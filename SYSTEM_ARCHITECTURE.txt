                            KEY DESIGN DECISIONS


1. PyTest Script Always Exits 0
   ────────────────────────────
   WHY: Allows Cypress to run even if PyTest fails
   HOW: Wrapper script checks junit.xml for actual status


2. Reports Always Generated
   ─────────────────────────
   WHY: Never lose failure information
   HOW: Script catches all errors and writes minimal summary


3. Both Hook and Wrapper
   ──────────────────────
   WHY: Cover all execution paths (direct cypress, npm script)
   HOW: Hook for cypress run, wrapper for proper exit codes


4. JUnit XML as Source of Truth
   ─────────────────────────────
   WHY: Reliable, parseable, CI-compatible
   HOW: Parse XML to determine pass/fail instead of exit codes


5. Error Categorization
   ────────────────────
   WHY: Quick failure diagnosis
   HOW: Heuristic matching on error messages

                           ARTIFACTS BREAKDOWN


reports/pytest/junit.xml
────────────────────────
- Standard JUnit XML format
- Machine-readable test results
- Used by CI systems (Jenkins, GitLab, GitHub Actions)
- Contains: test counts, durations, pass/fail status


reports/pytest/output.txt
─────────────────────────
- Complete pytest console output
- Includes full tracebacks
- Captured even on failure
- For deep debugging


reports/pytest/summary.md
─────────────────────────
- Human-readable markdown
- Categorized failures (AssertionError, AttributeError, etc.)
- Truncated to 30 lines per error (full in output.txt)
- Always generated, even on fatal errors
- Example sections:
  1. Test Results (counts)
  2. Failure Categories (grouped)
  3. Detailed Failures (per-test breakdown)
  4. Artifacts (file locations)
